# 櫃檯接手控制：LINE 原後台回覆

依使用者確認，LINE 接待採「原 LINE 後台聊天＋獨立控制頁接手／結案」。`/front-desk.html` 沿用原工作台網址，LINE 對話不再顯示人工寄送輸入框。管理員在櫃檯電腦登入一次後共用，不建立員工個別帳號，也不能辨認是哪一位員工操作。本版本未自動合併或啟用正式服務。

## LINE 操作流程

1. 在 LINE 原後台閱讀客人的完整訊息、照片與檔案。開啟接手控制頁，使用專用管理員密碼登入；不是 LINE／Facebook／GitHub 密碼。
2. 在控制頁選取對話，對照 LINE 客人及近期文字，勾選「我已在 LINE 核對這位客人及對話」。目前列表是通道及不透明對話代碼，不自動取得 LINE 暱稱；**無法確認是同一位客人時，不要接手這筆對話**。
3. 按「人工接手，暫停 AI」。若 AI 正在處理，先顯示「接手中」；等到「真人接手中・AI 已暫停」後，再回 LINE 回覆。已送往平台的訊息無法撤回。
4. 按「複製人工接手說明」，將「【真人櫃檯回覆】您好，接下來由真人櫃檯為您服務😊」貼至 LINE 的同一位客人聊天室，人工確認後送出。可依客人的語言調整問候。**複製按鈕及接手操作都不會自動發訊息。**
5. 所有後續人工文字、圖片與檔案繼續在 LINE 原後台處理。「開啟 LINE 官方帳號聊天」只開原後台，不會自動選取同一位客人；仍需自行核對。
6. 處理完回控制頁，留下簡短交接摘要，勾選「我已在原平台確認處理完成，並看過這位客人的最新訊息」，再按「處理完成，恢復 AI」。修改摘要、切換對話或收到新的文字更新，都需要重新確認。只有下一則客人訊息才由 AI 回覆；不另發自動結案訊息。

這個方案**仍需在接手與結束時操作控制頁**。直接在 LINE 原後台打字，不會自動觸發 AI 暫停、加人工標示或同步人工文字。AI 無法自行知道原平台已處理完成；交接摘要用於補上人工處理背景。客人要求寄信、寄信成功與櫃檯實際接手仍是不同狀態。

## AI 身分與其他通道

- LINE 與 Messenger 的 AI 文字在模型完成內容後、實際送往平台前，由共用函式統一加上 `【AI 小幫手】`；重複標示會正規化，不能沿用 `【真人櫃檯回覆】`。空內容不會變成一則只有身分標示的訊息。
- 這是發送層標示，不是新增關鍵字答題或改寫親切口吻。模型對話記憶保留原回覆內容，不把標示加入語意提示詞。日期、金額及訂房網址保持原內容。
- **AI 標示隨此版本部署生效，不受 `FRONT_DESK_ENABLED` 開關控制。** 控制頁則仍預設關閉，需另外完成設定。
- Messenger 保留既有受保護工作台人工回覆，伺服器加上 `【真人櫃檯回覆】`；仍須明確接手與結案。這次沒有新增 Meta 原後台人工回覆同步。
- 本次不建立瀏覽器擴充功能，也不攔截 LINE 登入、原生後台操作或手機 App。

## 暫停及恢復的統一規則

| 事件 | 該旅客的 AI 狀態 |
| --- | --- |
| 按人工接手，沒有執行中的回覆 | 暫停，開放真人回覆 |
| 按人工接手，AI 正在生成或送出 | 先阻止新 AI 動作，等待既有處理釋放後顯示可回 LINE 回覆 |
| 客人說好、謝謝、OK，或自行輸入恢復 AI | 保持人工接手，不解讀為結案指令 |
| 櫃檯登出、關閉頁面、登入逾期或久未操作 | 保持人工接手 |
| 接手超過 30 分鐘 | 開啟的工作台顯示待結案提醒，不自動恢復 |
| 原始對話或收件路由到期 | 保持人工接手；不能用到期資料發訊息 |
| 櫃檯結案時又有新的入站文字或工作台人工回覆 | 拒絕過期的結案，要求先讀最新訊息 |
| 具有效登入的櫃檯明確結案，摘要保存成功且版本仍一致 | 恢復 AI |

每位客人的狀態獨立，不會暫停其他客人的 AI。交接摘要僅是該段對話背景，不是新的飯店規則或已驗證的知識庫資料。結案會清除過期的寄信授權狀態，避免下一個「好」沿用舊確認。

## 目前涵蓋範圍與限制

- LINE 一對一文字與 Messenger 文字，顯示啟用後收到的對話；不匯入以前所有聊天紀錄。
- 不含 LINE 群組、圖片、檔案、語音、Instagram、網站或 Realtime Voice 的人工工作台。原有其他通道不因此變成人工可接手。
- 不自動擷取原平台的真人回覆，不做電話轉接，也不自動判斷員工已處理完畢。新訊息版本檢查涵蓋系統收到的文字；原平台人工文字、圖片／檔案不在版本檢查範圍，因此結案前還需人工核對原平台。
- 原本的客人語意理解、知識庫、訂房連結與寄信流程保持原核心；此 PR 的重點是人工接管及發送權，不是另一套關鍵字答題器。
- 工作台不是長期 CRM：只保留原對話服務設定的最近 20 則、24 小時滑動／48 小時絕對期限。電話、Email、卡號及密碼沿用原有遮蔽規則。
- 對話列表包含最近 50 位以及所有尚未結案的接手對話，不會把未結案項目因數量上限直接隱藏。頁面可見時每 30 秒更新，亦可手動更新；關閉頁面後不發背景通知。
- `accepted` 只代表平台接受請求，不代表旅客收到或已讀。遇到逾時或無法確認紀錄保存結果，顯示「尚未確認」，不自動重寄。原平台的封鎖、額度或投遞情況仍可能影響收件。

## 啟用前的管理員設定

本 PR 不新增真實密碼、不讀取／更換平台金鑰、不修改 Vercel 正式環境設定。以下值必須由管理員在部署環境的祕密設定區保存，**不要貼到聊天、PR、程式碼或網址**。

| 變數 | 用途 |
| --- | --- |
| `FRONT_DESK_ENABLED=true` | 明確啟用新工作台及文字通道接手功能，未設定時預設關閉 |
| `FRONT_DESK_ADMIN_KEY` | 至少 8、最多 256 字元的專用管理員密碼；系統不限制字元組合 |
| `FRONT_DESK_DATA_KEY` | 獨立的 32-byte 隨機金鑰，以 Base64 編碼，用來加密平台收件路由 |
| `FRONT_DESK_ORIGIN` | 正式 HTTPS origin，例如 `https://your-hotel.example`，不要加路徑或結尾斜線 |
| 原有 Redis REST、`CONVERSATION_HMAC_SECRET` | 持久狀態、一次性發送紀錄與不直接暴露身分的對話 ID |
| 原有 `LINE_CHANNEL_ACCESS_TOKEN`／`META_PAGE_ACCESS_TOKEN` | 分別用來發送 LINE／Messenger 人工回覆 |

可以在管理員的安全電腦各執行一次以下命令，產生兩個**不同**的值，再分別貼入部署平台的祕密設定。不要把輸出提交至 Git。

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

先在測試環境完成設定及驗收，再決定正式啟用。Vercel 預覽部署允許平台提供的自身 HTTPS origin，並要求完整 `VERCEL_GIT_COMMIT_SHA` 作獨立控制資料命名空間。測試還是要使用**獨立 Redis、HMAC、測試官方帳號／粉專**：只有新控制資料做命名空間隔離，不表示原有所有聊天資料、金鑰、或外部通道都自動隔離。

## 資料及安全設計

- 原始平台收件 ID 僅從通過既有簽章驗證的 webhook 取得，並核對 HMAC 對話 ID。AES-256-GCM 加密內容綁定對話及環境命名空間；瀏覽器不能傳入、覆寫或取得原始 recipient ID。
- 平台路由與最後一次旅客訊息時間保存 48 小時，舊事件不能覆蓋較新的時間。頁面瀏覽不延長平台回覆時限。
- 人工控制資料只含不透明 ID、狀態、版本與時間，不含客人原文／聯絡資料；接手期間無自動到期，只有明確結案才回到 AI。
- 每次登入使用隨機 session token，伺服器僅存其雜湊鍵；cookie 為 `__Host-`、HttpOnly、Secure、SameSite=Strict，12 小時到期。登出撤銷該 session，輪替管理員密碼撤銷既有登入；這些操作都不結案。
- 所有資料讀取及動作 API 都要求登入、精確 HTTPS Origin、POST JSON、欄位白名單，回應不快取。登入有不儲存 IP 的全域短期嘗試限制；這不是逐員工稽核或多因素身分驗證系統。
- 頁面使用獨立 script／CSS 與 CSP。客人內容以文字節點顯示，沒有插入 HTML；密碼、對話草稿與 token 不放入 localStorage／sessionStorage。接手／結案後不接受先前尚未完成的讀取結果覆蓋新狀態；連線失敗時收起操作區，等重新確認狀態後再操作。
- Redis Lua 狀態操作及 lease 負責發送權。AI 在外部寄信動作與最終送訊息前再檢查 epoch／lease。真人送出及結案互斥，過期分頁不能操作新的接手階段。
- 送出先寫入 48 小時一次性 journal，再呼叫平台。結果只存 request ID、時間、狀態與內容指紋，不重存聯絡內容。工作台的「查詢上次送出結果」走獨立唯讀動作，即使 journal 到期也不會重新送出。核對原平台後建立新回覆，是新的人工送出意圖。
- 收訊中的 inbound version 與對話 revision 同時保護結案：即使新訊息正好落在摘要保存和恢復 AI 之間，也保留人工狀態。失敗後可能已保存一筆處理摘要，但不會因此宣稱已結案。

## 平台限制與成本

本版 LINE 人工回覆由櫃檯在原後台送出，控制頁不呼叫 push API，複製接手說明也不送出訊息。原有受保護的 LINE 人工發送 API 保留相容，但不再由此頁呼叫；若另行使用該 API，push 與原本 webhook reply 不同，會計入 LINE 官方帳號的訊息用量。此版本不查好友關係，一律採最後一則客人一對一訊息後 7 天內的保守限制，且路由仍可能更早因 48 小時保存期限失效；這不是宣稱所有 LINE 好友都只有 7 天可回覆。[LINE push 條件](https://developers.line.biz/en/reference/messaging-api/#send-push-message)、[LINE 訊息用量](https://developers.line.biz/en/docs/messaging-api/pricing/)。

Messenger 限一般 24 小時回覆窗口，使用 `messaging_type: RESPONSE`，不假設已取得額外 HUMAN_AGENT 權限，不繞過平台政策。[Meta Messenger 政策](https://developers.facebook.com/documentation/business-messaging/messenger-platform/policy)。

工作台會增加 Vercel 請求與 Redis 讀寫用量，不新增另一個 AI 模型訂閱。列表使用分批讀取，背景分頁停止輪詢；仍應由管理員監看既有平台額度。此 PR 沒有查帳單、儲值或啟用付費方案。

## 驗證及上線檢核

已完成的自動化測試均使用虛構旅客、記憶體 Redis 命令模型、模型／寄信／平台替身；不對客人或櫃檯實際發送。`test/front-desk.test.js` 另透過可用的 `texlua` 執行未改寫的控制 Lua，Redis 及 cjson 邊界仍為測試替身。沒有安裝該選用 interpreter 的環境會明確 skip 這一項，不得把它算成已驗證。

```sh
npm test -- --test-reporter=dot
npm run lint
npm run typecheck
npm run build
```

本專案的 lint／typecheck／build 主要是 JavaScript 語法與差異格式檢查，並非完整 TypeScript 型別驗證、瀏覽器操作測試或實際資料庫整合驗證。新增的控制頁互動回歸測試執行真實頁面程式、模擬 DOM 與受保護 API，涵蓋 LINE 核對／複製不寄送、結案確認失效、自動更新競態及 Messenger 人工寄送；這不是實際瀏覽器驗收。AI 標示測試涵蓋兩個通道、控制頁開／關、LINE 無記憶備援、多語內容及恢復後續聊。

正式啟用前仍需管理員驗收：

- [ ] 在獨立測試環境驗證真正 Redis 的 Lua、TTL、連線故障與兩個分頁同時操作。
- [ ] 手機／櫃檯瀏覽器登入、切換對話、草稿、登出、session 到期及送出結果查詢。
- [ ] 使用管理員自己的測試 LINE 帳號確認 AI 身分、核對同一位客人、AI 暫停、複製後在原 LINE 貼上人工說明、原平台回覆、摘要及結案後續聊；另驗收 Messenger 工作台回覆。
- [ ] 在 AI 回覆途中接手、在結案途中傳入新訊息，確認沒有雙重回覆或誤結案。
- [ ] 驗證平台拒絕、逾時、額度不足、回覆窗口到期與原平台已讀狀態，不把 API accepted 當成已收件。
- [ ] 確認櫃檯知道此控制頁與 LINE 原生後台不同；接手和結束仍需切換。LINE 人工訊息不會自動同步或加標示，處理結果要留摘要，圖片／檔案必須在 LINE 確認。
- [ ] 確認 LINE push 用量、Redis／Vercel 額度，以及值班人員的待結案巡檢方式。

不保證零錯誤或自動理解所有交接情境。真人接手是明確權限狀態，不交由模型依「謝謝」「好了」猜測。

## 回復與故障處理

若只是關閉 `FRONT_DESK_ENABLED`，此版 webhook 仍會保留已存在的人工 hold，停止對該旅客回 AI；工作台停用期間也不能正常結案，應先處理完 hold 再停用入口。啟用期間資料庫狀態無法確認時採停止回覆，不走未受控的 AI 備援。

**不要在尚有接手對話時直接刪 Redis、換 HMAC、移轉命名空間或回滾到沒有 hold 檢查的舊程式。** 這些管理動作會破壞持久狀態保證。先在原平台確認所有待處理對話、完成結案，再由管理員安排設定／資料移轉；加密金鑰輪替也需處理舊路由，不會自動解密舊金鑰的資料。
